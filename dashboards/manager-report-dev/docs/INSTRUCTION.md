## 1. Назначение

Тестовый дашборд для разработки менеджерского отчёта (прототип «ИИ-РОП»). 
Данные читает из ratings-dashboard (тот же `deals_NEW.json`).

**Цель:** аналитика продаж по каждому менеджеру — воронка, KPI, срезы, отклонения от среднего.

### 2.2. Источники данных

`server.js` при старте загружает в память три файла из `ratings-dashboard/cache/`:

1. **`agg.json`** (~150 КБ) — агрегированные KPI, недели, форматы, edu.
   Используется для: `weeks[]`, `ytd`, `fmt_ytd`, статистики отдела.
   
2. **`deals_NEW.json`** (~20 МБ, ~28 414 сделок) — все сделки 2025–2026.
   Используется для: пересчёта метрик по менеджерам за выбранный период.
   Время загрузки: ~1 сек. Время фильтрации: <0.1 сек.
   
3. **`dicts.json`** — справочники (пользователи, категории, стадии, источники).
   Используется для: маппинга ASSIGNED_BY_ID → ФИО менеджера.

## 3. Правила расчёта (утверждены 22.06.2026)

### 3.1. Основные принципы

1. **Единственное правило с `OPPORTUNITY ≥ 11` — для paid (оплачено).** 
   Всё остальное (in_work_start, created, lost, mql, sql, invoice) — без проверки суммы.
   
2. **CLOSEDATE (дата закрытия) — не используется.**
   Отказ определяется только по `STAGE_SEMANTIC_ID = F`. 
   Дата проигрыша не важна — если проиграна, то проиграна.
   
3. **Дата оплаты = `UF_DATE_PAY_1C`** (поле «Дата оплаты из 1С»).
   Длительность сделки считается как `(PAY_DT - DATE_CREATE).days`.

4. **Категории:** 0 (Sale), 8 (PreSale), 19 (КОМ).
   Категории 0 и 19 — для воронки продаж.
   Категория 8 — для PreSale (MQL/SQL).

5. **Сделки создаются без лидов CRM.** 
   Поле `leads` — это `crm.lead` (входящие заявки), а `mql` — сделки PreSale/Sale. 
   Они могут не пересекаться (сделка создана напрямую, без лида).

### 3.2. Детальные правила

| Поле | Что считает | Условие | OPP≥11? | Период |
|---|---|---|---|---|
| `in_work_start` | Сделки в работе на начало периода | `DC ≤ cutoff` + `PAY_DT пусто` + `SEM ≠ F` + кат 0/19 | ❌ | 01.01.2026 или `from` |
| `created` | Создано за период | `DC` в периоде + кат 0/8/19 | ❌ | по DC |
| `paid` | Оплачено за период | `PAY_DT` в периоде + кат 0/8/19 | **✅ да** | по PAY_DT |
| `lost` | Проиграно за период | `SEM = F` + кат 0/8/19 | ❌ | всегда (SEM=F) |
| `mql` | Квалифицированные лиды | `is_qual_lead_w()` по DC | ❌ | по DC |
| `sql` | Передано в продажу | Стадии SQL+ (см. 3.3) | ❌ | по DC |
| `invoice_cnt` | Выставлено счетов | `UF_CRM_1753272713011` («Дата Счет отправлен») | ❌ | по дате счёта |

### 3.3. MQL

```
Sale (0):       все стадии, кроме NEW / UC_1YW3V2 / UC_STZB49 / UC_838R2R → MQL
PreSale (8):    не входит (не считается MQL)
КОМ (19):       всё, кроме WON (семантика S) и LOSE (семантика F) → MQL
```

### 3.4. SQL

```
1. Стадии DETAILS / PROPOSAL / 2 / 6 / WON → SQL (любая категория)
2. КОМ (19), SEM ≠ S:
   - стадии EXECUTING / UC_C670BC / UC_I443UQ → SQL
   - есть UF_CRM_5D133690E1 (roistat) + стадии UC_ALOZ6B / UC_W4ML6H / LOSE → SQL
3. Есть UF_CRM_1753272713011 (Дата Счет отправлен) + стадии:
   LOSE / UC_F2YC3N / UC_W6SCHG / UC_670ME2 / UC_VKPN0N → SQL
```

### 3.5. Конверсии

| Конверсия | Формула |
|---|---|
| Лид→MQL | `mql / leads × 100` |
| MQL→SQL | `sql / mql × 100` |
| SQL→Счёт | `invoice_cnt / sql × 100` |
| Счёт→Оплата | `paid / invoice_cnt × 100` |
| Конв. сделок | `paid / (paid + lost) × 100` |

### 3.6. Срезы (горизонтальные stacked bar)

**B2B vs B2C:** 
- B2B: есть `COMPANY_ID` (сделка привязана к компании)
- B2C: нет COMPANY_ID

**Источники:**
- Внутренняя база: SOURCE_ID из списка `INTERNAL_SRC`:
  `['79641902894','79641902977','79641902926','UC_7G65N9','79641902903','RECOMMENDATION']`
- Маркетинг: все остальные SOURCE_ID

**Форматы:**
- ООМ (Очное): UF_FORMAT = 19042467
- ОМ (Онлайн): UF_FORMAT = 19042468
- СДО (Видеокурс): UF_FORMAT = 19042469

### 4.2. Правило для autopay

`Гайдукова (516) + Щеткина (527) → строка «Автооплаты».`
Все сделки этих двух менеджеров суммируются в одну строку.

### 4.3. Правило для hidden

Все сделки скрытых (уволенных) менеджеров суммируются в строку **«Прочие»** (группа = `other`).
Это нужно, чтобы общая сумма поступлений (75 045 032 ₽) сходилась с YTD.

### 4.4. Новые ответственные

При появлении нового ASSIGNED_BY_ID (которого нет в MGR_GROUPS):
1. Спрашиваю у Ивана: «Появился новый ответственный X (ID). Кто это? Продавец, техника, автооплата, уволен?»
2. Без ответа — не включаю никуда (сделки попадают в «Прочие» на сервере, на фронте не отображаются).

## 5. Фронт (index.html)

### 5.1. Блоки

1. **Сводка KPI** — 6 карточек (оплачено, поступления, цикл, конверсия, проиграно, в работе)
2. **Селектор периода** — выпадашка: YTD / Январь … Июнь 2026
3. **Таблица 1: Основные показатели** — 14 колонок по каждому менеджеру
4. **Таблица 2: Конверсии и отклонения от среднего** — цветовая маркировка (зелёный/жёлтый/красный)
5. **Срезы (горизонтальные stacked bar)** — 3 графика: B2B/B2C, Источники, Форматы

### 5.2. Цветовая маркировка (Таблица 2)

| Отклонение от среднего | Цвет |
|---|---|
| > +10% | 🟢 зелёный (выше среднего) |
| ±10% | 🟡 жёлтый (около среднего) |
| < -10% | 🔴 красный (ниже среднего) |

Для `avg_dur`: инвертировано (меньше = лучше = зелёный).

### 5.3. Функции

| Функция | Описание |
|---|---|
| `n(v)` | Форматирование числа (пробелы-разделители) |
| `p(v)` | Процент с 1 знаком после запятой |
| `e(s)` | Экранирование HTML |
| `bdg(v,lo,hi)` | Цветовой badge |
| `sum(arr,k)` | Сумма по ключу |
| `wavg(arr,k,w)` | Взвешенное среднее |
| `tab1(mgrs)` | Рендер таблицы 1 |
| `tab2(mgrs)` | Рендер таблицы 2 |
| `renderBars(mgrs)` | Рендер stacked bar (3 среза) |

## 7. Известные ограничения и TODO

- **edu_*** — нулевые (поле UF_CRM_1765896709800 не заполнено для большинства сделок)
- **Срезы edu** — убраны из баров (все 0), ожидается заполнение в CRM
- **Фильтр периода** — только по месяцам, не по неделям (можно добавить)
- **Bond и Афанасьев** — отображаются отдельно, но их логика ещё уточняется
- **tech с поступлениями** — сигнализировать при появлении (сейчас ~3 млн)
