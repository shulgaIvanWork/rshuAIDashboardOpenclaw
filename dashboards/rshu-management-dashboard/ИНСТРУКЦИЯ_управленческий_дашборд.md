## 1. Источники данных

### 1.1. Воронки (категории сделок)

В дашборде участвуют **3 воронки**:

| ID | Название | Описание |
|---:|---|:---|
| 0 | **Sale** («Общая (по умолчанию)») | Основные продажи |
| 8 | **Pre Sale** | Предпродажная подготовка (лиды до передачи в ОП) |
| 19 | **КОМ (Sale)** | Корпоративное обучение (B2B-проекты) |

### 1.2. Что НЕ входит

Категории, которые **исключены** из расчётов:
- Post Sale (категория 9) — постпродажное сопровождение
- Аккаунтинг (категория 10)
- Отказы (категория 12)
- Repeat Sale (категория 13)
- Реанимация (категория 20)
- Сделки из других категорий

### 1.3. Период данных

- **2024–2026 годы** (по DATE_CREATE) — всего ~56 190 сделок по 3 воронкам
- **С начала года = с 1 января 2026 по текущую дату**
- **Поступления** — по дате UF_DATE_PAY_1C (без ограничения по году создания)

### 1.4. Технические ограничения

- **Минимальная сумма сделки для учёта:** 1 ₽ (MIN_OPP = 1.0)
- **Технические сделки (сумма = 0, статус «счёт оплачен»)** — НЕ считаются нигде и никогда
- Данные обновляются инкрементально: разово полная выгрузка, далее только новые и изменённые за последнюю неделю

## 2. Базовые правила

### 2.1. Деление ООМ / КОМ

Сделка считается **КОМ (Корпоративное обучение)**, если выполняется **любое** из условий:
1. **Галочка** `UF_CRM_1683882427069` = `Y` (поле «КОМ»)
2. **Формат** `UF_FORMAT` = «КОМ» (ID=19042498)
3. **Направление** `UF_CRM_1498466811` = «Корпоративное обучение» (ID=1906)
4. **Категория** = 19 «КОМ Sale»
5. **Тип обучения** `UF_CRM_1765896709800` = «КОМ» (ID=34765)

**ООМ (Открытое обучение)** = всё остальное из трёх воронок.

### 2.2. Поступления (доход)

**Главное правило: ТОЛЬКО по дате оплаты из 1С (`UF_DATE_PAY_1C`).**
CLOSEDATE не используется. Fallback на CLOSEDATE — НЕТ.

| Ситуация | Семант.статус | `UF_DATE_PAY_1C` | Сумма | Что делаем |
|:---|:---:|:---:|:---:|:---|
| ✅ Счёт оплачен | S (WON) | есть | > 0 | **Считаем** в доход. Это основное поступление |
| 🔄 Возврат | F (LOSE) | есть | любая | **Считаем** в доход, но показываем отдельно — блок «Возвраты покупателям» (сумма и кол-во) |
| ⚠️ Артефакт | P (в работе) | есть | любая | Пишем Ольге **на проверку** |
| ❓ Без даты | S (WON) | **нет** | любая | **НЕ считаем**. Пишем Ольге |
| 🚫 Техническая | S (WON) | есть/**нет** | **= 0** | **НЕ считаем** никуда (не портит конверсию и средний чек) |

**Формула поступлений:**
```
Доход = сумма OPPORTUNITY по сделкам где:
  UF_DATE_PAY_1C IS NOT NULL
  AND OPPORTUNITY > 0
  AND STAGE_SEMANTIC_ID = 'S' (WON)
```

**Возвраты (отдельный блок):**
```
Возвраты = сумма OPPORTUNITY по сделкам где:
  UF_DATE_PAY_1C IS NOT NULL
  AND OPPORTUNITY > 0
  AND STAGE_SEMANTIC_ID = 'F' (LOSE)
```
Выводятся отдельной строкой/кнопкой под основными поступлениями.

### 2.3. Путь сделки

1. **Pre Sale** → приходят и ООМ, и КОМ
2. **КОМ Sale** (кат. 19) → сюда уходят КОМ на проработку
3. **Sale** → сюда возвращаются на оплату (и ООМ, и КОМ)
4. **WON всегда в Sale**

### 2.4. Лиды

**Лиды = количество созданных сделок** (не объекты `crm.lead`).

Считаем по `DATE_CREATE` в периоде, по **3 воронкам вместе**:
- Pre Sale (кат. 8): все созданные
- Sale (кат. 0): все, **кроме технических** (сумма = 0 + счёт оплачен)
- КОМ Sale (кат. 19): все созданные

### 2.5. Воронка — 5 этапов

| Этап | Название | Правило |
|:---:|---|---|
| 1 | 📥 **Лиды** | Все созданные сделки в PreSale + Sale + КОМ Sale (без тех.) |
| 2 | 🔍 **MQL** | Прошли PreSale И находятся в Sale на стадиях: MQL, SQL, Счёт отправлен, Постоплата, Частично оплачен, Счёт оплачен, Закрыто, Предзакрытие в отказ, Приоритет, Следующий год. + сделки в КОМ Sale |
| 3 | 🎯 **SQL** | Прошли КОМ Sale (были в C19) ИЛИ находятся в Sale от стадии SQL: SQL, Счёт отправлен, Постоплата, Частично оплачен, Счёт оплачен, Закрыто, Предзакрытие в отказ |
| 4 | 📄 **Счёт отправлен** | Были в стадиях Счёт отправлен/дальше + есть `UF_CRM_1753272713011` («Дата Счет отправлен») в периоде |
| 5 | ✅ **Оплачено** | `UF_DATE_PAY_1C` + WON + сумма > 0 (правило 2.2) |

### 2.6. Стадии воронки Sale (категория 0)

| Код стадии | Название | Этап воронки |
|:---:|---|---|
| `NEW` | Исходный лид | — |
| `UC_4RJOR4` | Маркетинговый лид (MQL) | MQL |
| `DETAILS` | Лид для продажи (SQL) | MQL, SQL |
| `PROPOSAL` | Счёт отправлен | MQL, SQL, Счёт отправлен |
| `2` | Постоплата | MQL, SQL, Счёт отправлен |
| `6` | Частично оплачен | MQL, SQL, Счёт отправлен |
| `WON` | Счёт оплачен | MQL, SQL, Счёт отправлен |
| `LOSE` | Закрыто и не реализовано | MQL, SQL, Счёт отправлен |
| `UC_F2YC3N` | Предзакрытие в отказ | MQL, SQL, Счёт отправлен |
| `UC_VKPN0N` | Приоритет | MQL |
| `UC_W6SCHG` | Следующий год | MQL |

### 2.7. Поля CRM для дат

| Назначение | Поле | Тип |
|:---|:---:|:---:|
| Дата оплаты из 1С | `UF_DATE_PAY_1C` | date |
| Дата счёт отправлен | `UF_CRM_1753272713011` | date |
| Номер счета | `UF_CRM_1475610135` | string |

### 2.8. Конверсии воронки

| Метрика | Формула |
|:---|---:|
| MQL → SQL | `SQL / MQL × 100%` |
| SQL → Счёт | `Счёт / SQL × 100%` |
| Счёт → Оплата | `Оплата / Счёт × 100%` |
| Общая конверсия Sale | `WON / (WON + LOSE) × 100%` |

### 2.9. Скорость закрытия

**Срок WON (оплата):** от `DATE_CREATE` до `UF_DATE_PAY_1C` (дни).
- Простая средняя, взвешенная (по сумме), медиана

### 2.10. B2B / B2C

| Условие | Тип |
|:---|---|
| Есть `COMPANY_ID` | B2B |
| Категория = КОМ (Sale) | B2B |
| Сумма ≥ 50 000 ₽ | B2B |
| Остальное | B2C |

### 2.11. Форматы обучения

Определяются по приоритету:
1. Поле `UF_FORMAT` (инфоблок 149) — точное значение
2. Fallback по ключевым словам в названии сделки:
   - «(СДО)», «сдо» → СДО
   - «онлайн», «дистанц» → ОМ (Онлайн)
   - «в г.», «Москва», город → ООМ (Очное)
   - КОМ (категория 19) → КОМ (всегда)

### 3.4. Участники ООМ/ОМ (2 вкладки)

**Прошлая неделя / Текущая неделя.**

Участники = WON-сделки формата ООМ (Очное) или ОМ (Онлайн),
у которых период обучения (`UF_CRM_DATE_START_LEARN` / `UF_CRM_DATE_END_LEARN`)
пересекается с выбранной неделей.

Если дат обучения нет — fallback на `CLOSEDATE`.

Регион участника определяется:
1. Из `contacts_ext.json` (регион контакта)
2. Fallback на регион компании (`companies_ext.json`)

## 6. Ограничения и нюансы

1. Export API имеет лимит offset = 5000. Для полной выгрузки — помесячная/понедельная разбивка.
2. Старые закрытые сделки — статичны. При инкрементальном обновлении трогаем только изменённые за неделю.
3. С начала года — сделки, оплаченные (UF_DATE_PAY_1C) в периоде.
4. Артефакты оплат (P + UF_DATE_PAY_1C и F + UF_DATE_PAY_1C) — выводятся отдельными блоками (возвраты, на проверку).
5. Данные из Roistat и Яндекс Метрики — не подключены, только CRM.

## 7. Баги и их решения

### 7.1. Export API — даты в формате ДД.ММ.ГГГГ (06.06.2026)
**Проблема:** Export API возвращает даты в формате `ДД.ММ.ГГГГ`, а старый REST API — в `ГГГГ-ММ-ДД`.
Фильтр по году `dc[:4]` для даты `"06.06.2026"` даёт `"06.0"`, а не `"2026"`.
Все Export API-сделки отфильтровывались, YTD = 0.
**Решение:** Проверять 3-й символ: если `dc[2] == '.'` — формат ДД.ММ.ГГГГ, год = `dc[6:10]`.
`parse_dt()` должен пробовать оба формата.

### 7.2. Export API — лимит offset ≤ 5000
**Проблема:** Max offset = 5000. Нельзя получить >5050 записей за один проход.
Для категории Sale (160k) нужно разбивать запросы.
**Решение:** Курсорная пагинация по `>ID`:
1. Взять 5050 записей (offset 0..5000)
2. Запомнить `last_id`
3. Следующий проход: `>ID=last_id`, offset=0..5000
4. Повторять до пустого ответа

### 7.3. Старый REST API — фильтр по дате игнорируется
**Проблема:** `crm.deal.list?>=DATE_CREATE=2025-01-01` возвращает ВСЕ сделки,
включая ID=1 из 2007 года. Фильтр не работает.
**Решение:** Использовать только Export API для новых данных,
старый дамп (deals_all.json) — как базу для исторических данных.

### 7.4. Export API — ключ доступа с символом … (многоточие)
**Проблема:** При копировании из интерфейса ключ может содержать
символ `` (U+2026) вместо полного текста: `14b0fc…753f`.
API возвращает `invalid_key`.
**Решение:** Проверять длину ключа (32 символа для hex).
Ключ: `14b0fc053c141e47a5974b3859f5753f`

### 7.5. urllib.urlencode с doseq=True — неправильный формат
**Проблема:** `urlencode({"data": data}, doseq=True)` для вложенного dict
генерирует `data=FILTER&data=SELECT` вместо `data[FILTER][CATEGORY_ID]=0`.
Export API не понимает такой формат.
**Решение:** Использовать ручную `flatten()` функцию, которая строит
PHP-стиль параметры: `data[FILTER][CATEGORY_ID]=0`.

### 7.6. Export API — SECRET в файлах маскируется
**Проблема:** При записи через `edit()` ключ маскируется
как `14b0fc…753f` (с многоточием) вместо полного значения.
Скрипт работает с невалидным ключом, API возвращает ошибку.
**Решение:** Проверять `SECRET` перед запуском. Записывать полный ключ
через `python3 -c "content.replace(...)"`.
