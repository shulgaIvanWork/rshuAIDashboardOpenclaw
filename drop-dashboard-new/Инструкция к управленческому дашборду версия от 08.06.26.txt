## 1. Источники данных

### 1.1. Воронки (категории сделок)

В дашборде участвуют **3 воронки**:

| ID | Название | Описание |
|---:|---|:---|
| 0 | **Sale** («Общая (по умолчанию)») | Основные продажи |
| 8 | **Pre Sale** | Предпродажная подготовка (лиды до передачи в ОП) |
| 19 | **КОМ (Sale)** | Корпоративное обучение (B2B-проекты) |

### 1.2. Что НЕ входит

Категории, которые **исключены** из расчётов:
- Post Sale (категория 9) — постпродажное сопровождение
- Аккаунтинг (категория 10)
- Отказы (категория 12)
- Repeat Sale (категория 13)
- Реанимация (категория 20)
- Сделки из других категорий

### 1.3. Период данных

- **2024–2026 годы** (по DATE_CREATE)
- **С начала года = с 1 января 2026 по текущую дату**
- **Поступления** — по дате UF_DATE_PAY_1C (без ограничения по году создания)

### 1.4. Технические ограничения

- **Минимальная сумма сделки для учёта:** 1 ₽ (MIN_OPP = 1.0)
- **Технические сделки (сумма = 0, статус «счёт оплачен»)** — НЕ считаются нигде и никогда
- Данные обновляются через CRM Export API (курсорная пагинация, offset ≤ 5000)

### 1.5. CRM Export API

- **Эндпоинт:** `https://24.uprav.ru/web_services/crm/export.php`
- **Методы:** `getDeals`, `getFormats`, `getDirections`, `getUserFieldsCrm`
- **Пагинация:** limit ≤ 50, offset ≤ 5000, курсор через `>ID`
- **Обогащение:** COMPANY (ID, TITLE), CONTACT (NAME, LAST_NAME), CATEGORY_NAME, STAGE_NAME, FORMAT_NAME, DIRECTION
- **WITH_PRODUCTS=Y** — для товаров/модулей (limit ≤ 5)

## 2. Базовые правила

### 2.1. Деление ООМ / КОМ

Сделка считается **КОМ (Корпоративное обучение)**, если выполняется **любое** из условий:
1. **Галочка** `UF_CRM_1683882427069` = `Y` (поле «КОМ»)
2. **Формат** `UF_FORMAT` = «КОМ» (ID=19042498)
3. **Направление** `UF_CRM_1498466811` = «Корпоративное обучение» (ID=1906)
4. **Категория** = 19 «КОМ Sale»
5. **Тип обучения** `UF_CRM_1765896709800` = «КОМ» (ID=34765)

**ООМ (Открытое обучение)** = всё остальное из трёх воронок.

### 2.2. Поступления (доход)

**Главное правило: ТОЛЬКО по дате оплаты из 1С (`UF_DATE_PAY_1C`).**
CLOSEDATE не используется. Fallback на CLOSEDATE — НЕТ.

| Ситуация | Семант.статус | `UF_DATE_PAY_1C` | Сумма | Что делаем |
|:---|:---:|:---:|:---:|:---|
| ✅ Счёт оплачен | S (WON) | есть | > 0 | **Считаем** в доход. Это основное поступление |
| 🔄 Возврат | F (LOSE) | есть | любая | **Считаем** в доход, но показываем отдельно — блок «Возвраты покупателям» |
| ⚠️ Артефакт | P (в работе) | есть | любая | Пишем Ольге **на проверку** |
| ❓ Без даты | S (WON) | **нет** | любая | **НЕ считаем** |
| 🚫 Техническая | S (WON) | есть/**нет** | **= 0** | **НЕ считаем** никуда |

**Формула поступлений:**
```
Доход = сумма OPPORTUNITY по сделкам где:
  UF_DATE_PAY_1C IS NOT NULL
  AND OPPORTUNITY > 0
  AND STAGE_SEMANTIC_ID = 'S' (WON)
```

**Возвраты (отдельный блок):**
```
Возвраты = сумма OPPORTUNITY по сделкам где:
  UF_DATE_PAY_1C IS NOT NULL
  AND OPPORTUNITY > 0
  AND STAGE_SEMANTIC_ID = 'F' (LOSE)
```

### 2.3. Путь сделки

1. **Pre Sale** → приходят и ООМ, и КОМ
2. **КОМ Sale** (кат. 19) → сюда уходят КОМ на проработку
3. **Sale** → сюда возвращаются на оплату (и ООМ, и КОМ)
4. **WON всегда в Sale**

### 2.4. Лиды

**Лиды = количество созданных сделок** (не объекты `crm.lead`).

**Технические сделки** (WON + OPPORTUNITY = 0) — НЕ считаются нигде.

#### 2.4.1. Лид сейл (квалифицированные лиды / квал лиды)

Сделки, которые прошли квалификацию:

| Воронка | ID | Правило |
|:---|---:|:---|
| **Sale** (Общая) | 0 | Все стадии **кроме NEW** (неквалифицированные) и **WON** (уже оплата). Не технические (OPPORTUNITY > 0) |
| **КОМ Sale** | 19 | **Все** сделки — они сразу квалифицированные |
| **Pre Sale** | 8 | **Не входит** — это предварительная квалификация |

**Какие стадии Sale входят в квал лиды:**
MQL (`UC_4RJOR4`), SQL (`DETAILS`), Счёт отправлен (`PROPOSAL`), Постоплата (`2`), Частично оплачен (`6`), Закрыто/LOSE (`LOSE`), Предзакрытие в отказ (`UC_F2YC3N`), Приоритет (`UC_VKPN0N`), Следующий год (`UC_W6SCHG`)

**Не входят в квал лиды:**
- `NEW` — неквалифицированные
- `WON` — уже оплачено, не лид
- Технические (OPPORTUNITY = 0)

#### 2.4.2. Все лиды

| Воронка | ID | Правило |
|:---|---:|:---|
| **Sale** | 0 | Все созданные, **кроме технических** (WON + 0₽) |
| **Pre Sale** | 8 | Все созданные, **кроме WON** (WON в PreSale = копия для статистики) |
| **КОМ Sale** | 19 | Все созданные, **кроме WON** (WON в КОМ = копия для статистики) |

Формула: **Все лиды = Квал лиды (лид сейл) + PreSale (без WON-копий)**

### 2.5. Воронка — 5 этапов

| Этап | Название | Правило |
|:---:|---|---|
| 1 | 📥 **Лиды** | Все созданные сделки в PreSale + Sale + КОМ Sale (без тех.) |
| 2 | 🔍 **MQL** | Прошли PreSale И находятся в Sale на стадиях: MQL, SQL, Счёт отправлен, Постоплата, Частично оплачен, Счёт оплачен, Закрыто, Предзакрытие в отказ, Приоритет, Следующий год. + сделки в КОМ Sale |
| 3 | 🎯 **SQL** | Прошли КОМ Sale (были в C19) ИЛИ находятся в Sale от стадии SQL: SQL, Счёт отправлен, Постоплата, Частично оплачен, Счёт оплачен, Закрыто, Предзакрытие в отказ |
| 4 | 📄 **Счёт отправлен** | Были в стадиях Счёт отправлен/дальше + есть `UF_CRM_1753272713011` («Дата Счет отправлен») в периоде |
| 5 | ✅ **Оплачено** | `UF_DATE_PAY_1C` + WON + сумма > 0 |

### 2.6. Стадии воронки Sale (категория 0)

| Код стадии | Название | Этап воронки |
|:---:|---|---|
| `NEW` | Исходный лид | — |
| `UC_4RJOR4` | Маркетинговый лид (MQL) | MQL |
| `DETAILS` | Лид для продажи (SQL) | MQL, SQL |
| `PROPOSAL` | Счёт отправлен | MQL, SQL, Счёт отправлен |
| `2` | Постоплата | MQL, SQL, Счёт отправлен |
| `6` | Частично оплачен | MQL, SQL, Счёт отправлен |
| `WON` | Счёт оплачен | MQL, SQL, Счёт отправлен |
| `LOSE` | Закрыто и не реализовано | MQL, SQL, Счёт отправлен |
| `UC_F2YC3N` | Предзакрытие в отказ | MQL, SQL, Счёт отправлен |
| `UC_VKPN0N` | Приоритет | MQL |
| `UC_W6SCHG` | Следующий год | MQL |

### 2.7. Поля CRM для дат

| Назначение | Поле | Тип |
|:---|:---:|:---:|
| Дата оплаты из 1С | `UF_DATE_PAY_1C` | date |
| Дата счёт отправлен | `UF_CRM_1753272713011` | date |
| Номер счета | `UF_CRM_1475610135` | string |
| Галочка КОМ | `UF_CRM_1683882427069` | boolean |
| Направление | `UF_CRM_1498466811` | enum (множественный) |

### 2.8. Конверсии воронки

| Метрика | Формула |
|:---|---:|
| Лиды → MQL | `MQL / Лиды × 100%` |
| MQL → SQL | `SQL / MQL × 100%` |
| SQL → Счёт | `Счёт / SQL × 100%` |
| Счёт → Оплата | `Оплата / Счёт × 100%` |
| Общая конверсия Sale | `WON / (WON + LOSE) × 100%` |

### 2.9. Скорость закрытия

**Срок WON (оплата):** от `DATE_CREATE` до `UF_DATE_PAY_1C` (дни).
- Простая средняя, взвешенная (по сумме), медиана

**Срок Pre Sale:** от создания в Pre Sale до перехода в Sale (дни).

### 2.10. B2B / B2C

| Условие | Тип |
|:---|---|
| Есть `COMPANY_ID` (не пустой, не "0") | B2B |
| Категория = КОМ (Sale) | B2B |
| Остальное | B2C |

### 2.11. Форматы обучения

Определяются по приоритету:
1. Поле `UF_FORMAT` (инфоблок 149) — точное значение
2. Fallback по ключевым словам в названии сделки:
   - «(СДО)», «сдо» → СДО
   - «онлайн», «дистанц» → ОМ (Онлайн)
   - «в г.», «Москва», город → ООМ (Очное)
   - КОМ (категория 19) → КОМ (всегда)

### 2.12. MBA / MMBA

**Отбор:**
1. Направление `UF_CRM_1498466811` = MBA (1917) или MMBA (35288)
2. Fallback: если в названии сделки есть «mba», «mmba», «mini mba»

**Подтипы (по названию):**
- `Mini MBA.Классический` / `Mini MBA.Классический` — классика
- `MBA.Эксперт` / `MBA Expert` — экспертная программа
- `MMBA.Специализация` / `MMBA Specialization` — специализация
- `Микро (Micro MBA)` / `Micro MBA` — микро-программа
- `MBA / MMBA` — остальные

## 3. Экраны дашборда — 14 блоков

**Цветовая легенда (везде где есть цвета):**

- 🟡 Жёлтый = в работе
- 🔴 Красный = отказы / плохо
- 🔵 Синий = внутренняя база (исходящие продажи)
- 🟠 Оранжевый = входящий трафик (маркетинг)
- 🟦🟧🟨 Шкала форматов: 🟦 очный, 🟧 онлайн, 🟨 СДО, 🟥 КОМ

### 3.1. KPI — 3 строки × 7 карточек

**Что это:** Быстрый взгляд на ключевые цифры года — отдельно по Общей воронке, ООМ и КОМ.

**Строка 1 — ОБЩАЯ (ООМ + КОМ вместе)**
Строка 2 — ООМ (Открытое обучение — частные лица, курсы)
Строка 3 — КОМ (Корпоративное обучение — B2B-проекты)

**7 карточек в каждой строке:**

| № | Что | Формула | Откуда |
|:---:|---|---|---|
| 1 | 📊 **Поступления YTD** | Сумма OPPORTUNITY (UF_DATE_PAY_1C + WON + >0) | `ytd.postupleniya` |
| 2 | 📋 **Лиды YTD** | Создано сделок (PreSale+Sale+КОМ, без тех.) | `leads_ytd` |
| 3 | 📈 **Конверсия YTD** | WON / (WON+LOSE) × 100% | `ytd.conv_deal_pct` |
| 4 | 💰 **Средний чек YTD** | Поступления / кол-во сделок | `ytd.avg_check` |
| 5 | ⏱ **Срок WON, дн.** | DATE_CREATE → UF_DATE_PAY_1C (среднее) | `ytd.avg_close_days_won` |
| 6 | 📈 **Неделя: поступления** | Сумма оплат за текущую неделю + дельта к прошлой | `cur.postupleniya` + `prev.postupleniya` |
| 7 | 🎯 **Неделя: лиды** | Лиды за текущую неделю + дельта к прошлой | `leads_cur` + `leads_prev` |

**Визуал:**
- 3 ряда карточек (плитки), по 7 карточек в ряд
- Общая — золотая полоса сверху карточки
- ООМ — своя полоса
- КОМ — бордовая полоса
- Под каждым рядом подпись: «ОБЩАЯ (ООМ + КОМ) · W23 (01.06—06.06)»

**Дельта (↑/↓):**
- ↑ зелёный = рост к прошлой неделе
- ↓ красный = падение к прошлой неделе
- → серый = без изменений
- Подпись: «+5.2%» или «-12.3%»

**Как читать:**
1. Сначала смотрим на Общую строку — общая картина
2. Потом ООМ и КОМ — за счёт кого результат
3. Если ООМ растёт, а КОМ падает — менеджеры лучше продают открытые курсы
4. **Срок WON** — если >60 дней, сделки закрываются долго

### 3.2. Воронка продаж — 5 этапов

**Что это:** Показывает, сколько сделок на каждом этапе и как они отсеиваются.

**Данные по неделям.**

**5 этапов:**
| Этап | Откуда |
|:---:|---|
| 📥 Лиды | PreSale+Sale+КОМ созданные (без тех.нулевых) |
| 🔍 MQL | Прошли PreSale И в Sale на MQL+ + КОМ Sale |
| 🎯 SQL | Прошли КОМ ИЛИ в Sale от SQL+ |
| 📄 Счёт | Стадии PROPOSAL+ + UF_CRM_1753272713011 |
| ✅ Оплачено | UF_DATE_PAY_1C + WON + >0 |

**Визуал:**
- **Stacked bar** (столбчатый с накоплением) по неделям
- 3 цвета: 🔵 MQL (синий), 🟡 SQL (золотой), 🟢 Оплачено (зелёный)
- По оси X — недели (W01, W02, ..., W24)
- По оси Y — количество сделок

**Как читать:**
1. Чем шире полоска — тем больше сделок
2. Сужение к зелёному = естественный отсев от MQL к оплате
3. Если синего много, а зелёного мало — конверсия плохая
4. Сравнивать последние недели — есть ли рост

### 3.3. Конверсии воронки — 4 линии

**Что это:** Эффективность переходов между этапами воронки.

**4 линии:**
- Лиды → MQL %
- MQL → SQL %
- SQL → Счёт %
- Счёт → Оплата %

**Визуал:**
- **Линейный график** по неделям
- Каждая линия своего цвета
- По оси Y — проценты (0%–100%)
- Подписи значений возле точек

**Как читать:**
1. Падающая линия = конверсия ухудшается
2. Если MQL→SQL упал ниже 30% — менеджеры не обрабатывают лиды
3. Если Счёт→Оплата ниже 50% — проблемы с выставлением/оплатой счетов
4. Последние 2-3 недели — текущий тренд

### 3.4. Поступления по неделям

**Что это:** Динамика выручки понедельно.

**Формула:** Сумма OPPORTUNITY по оплаченным (WON + UF_DATE_PAY_1C + >0), сгруппированная по ISO-неделям даты оплаты.

**Визуал:**
- **Столбчатый график**
- Синие столбцы
- Подписи сверху столбцов (если >1M — «1.5M», >100k — «150k»)
- По оси X — недели

**Как читать:**
1. Высота столбца = объём недели
2. Пустой столбец = выходная / нет оплат
3. Сравнивать последнюю неделю с предпоследней
4. Еженедельная динамика — ровный рост или скачки

### 3.6. Рейтинг источников

**Что это:** Какие каналы приносят деньги.

**Два типа источников:**
- 🔵 **Внутренняя база** (синий) = аккаунтинг, репитсейл, реанимация, холодная база, апсейл — исходящие продажи
- 🟠 **Входящий трафик** (оранжевый) = сайт, директ, коллтрекинг, регистрации, демо-уроки — маркетинг

**Определение типа:**
- Источник считается внутренней базой, если название содержит: "Аккаунтинг", "Repeat", "Upsale", "Реанимация", или SOURCE_ID = аккаунтинг/репит/upsale
- Всё остальное — входящий трафик

**Визуал:**
- Два горизонтальных bar-графика ТОП-5 (входящие слева, внутренняя база справа)
- Слева от бара — название источника
- Справа — сумма, кол-во сделок

## 6. Ограничения и нюансы

1. Export API имеет лимит offset = 5000. Для полной выгрузки — курсорная пагинация по `>ID`.
2. Старые закрытые сделки — статичны. При инкрементальном обновлении трогаем только изменённые за последнюю неделю.
3. Поступления считаются только по UF_DATE_PAY_1C (дата оплаты из 1С).
4. Возвраты (F + UF_DATE_PAY_1C) считаются в доход, но выводятся отдельным блоком.
5. Артефакты (P + UF_DATE_PAY_1C) — выводятся на проверку.
6. Компании и контакты обогащаются прямо в Export API (не нужен отдельный REST API).
7. Roistat и Яндекс Метрика — не подключены, данные только из CRM.

## 7. Баги и их решения

### 7.1. Export API — даты в формате ДД.ММ.ГГГГ
**Решение:** Проверять 3-й символ: если `dc[2] == '.'` — формат ДД.ММ.ГГГГ.

### 7.2. Export API — лимит offset ≤ 5000
**Решение:** Курсорная пагинация по `>ID` — взять 5050 записей (offset 0..5000), запомнить last_id, следующий проход с `>ID=last_id`.

### 7.3. Старый REST API — фильтр по дате игнорируется
**Решение:** Использовать только Export API для новых данных.

### 7.4. Merge.py портит данные
**Решение:** Не запускать merge.py. Использовать прямой анализ (analyze_new.py) без merge.

### 7.5. company_contact.json не содержит ID оплаченных сделок
**Решение:** Брать COMPANY_ID из сделки (поле `COMPANY_ID`), а не из company_contact.json.
